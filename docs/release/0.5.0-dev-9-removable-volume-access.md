# Lumi 0.5.0-dev-9 — reliable removable-volume access

Date: 2026-08-22

This development build completes the USB playback work from dev-8 for the
installed SMAppService architecture. Both the macOS app and its embedded engine
helper now declare why they require read-only access to removable volumes, so
macOS can present and persist the correct consent instead of leaving a USB scan
blocked in the background helper.

Packaging verification now fails if either declaration is missing. The scan UI
also explains that macOS may request removable-volume access and reiterates that
Lumi does not modify the disk.

## Verified with the connected `DJ VIC GRAY` USB

1. OneLibrary scan completed with 77 playlists and 1,156 tracks.
2. `Genre 5 Stars/MainStage 140+` synchronized 63 tracks read-only.
3. The two historical GRAY identities consolidated to one trusted, connected
   source.
4. All 63 synchronized tracks received a mounted, source-specific audio path;
   every referenced file existed on the USB.
5. `90s Bitch - Extended Mix` retained its Lumi-owned revision 36 timeline.
6. `Alice & Tina - Extended Mix` loaded and played from the USB in both Track
   Editor and Local Playback Deck A.
7. Database integrity, the full Rust workspace, the complete Apple application
   verification, app-bundle identity, arm64 binaries, code signatures, DMG,
   checksum, and SBOM all passed locally.

Because development builds use ad-hoc signing, macOS may ask for removable-volume
consent again when a newly signed development bundle replaces an older one.
