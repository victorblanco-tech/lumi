# Lumi 0.6.4-dev-35 — retain logical cue completion

Dev-34 hardware acceptance exposed duplicate buildup commands under different
MIDI generations, within the same transport epoch, load, plan revision and
phrase. Forecasting the next cue replaced the executor's single state slot;
the delayed current-phrase notification could then request the completed cue
again and cancel the next forecast.

The executor now keeps a separate completed-through watermark. Scheduling or
cancelling unsent work cannot erase it. A completed or earlier phrase in that
same context is rejected without mutating the pending next cue. A new execution
epoch (Start, confirmed seek/loop re-entry) clears it; another load, deck or plan
revision is a distinct identity. Only confirmed emission advances completion.
Failed/cancelled unsent work remains retryable. Storage and lookup are constant
size, with no extra I/O or SoundSwitch timeline manipulation.

The regression reproduces the hardware ordering (phrase 12 sent, phrase 13
forecast, phrase 12 notification delayed). It failed before the fix and must
leave the future cue untouched after the fix. Tests also cover cancellation,
failure/retry, plan revision and new-epoch re-entry.

This does not fix or explain the independently observed gaps in received CDJ
beat/status messages. Physical light beat alignment is not inferred from MIDI
deadline measurements. Hardware/UI acceptance is pending below.

## Validation and interruption

- Engine: 166 passed, 4 ignored; MIDI and Pro DJ Link regression suites passed.
- Clippy with warnings denied passed after descriptive test assertions replaced
  bare unwraps. The packaged runtime code is unchanged by that test-only edit.
- Dev-35 DMG built and verified; not yet installed/launched for hardware acceptance.
- Hardware testing was interrupted by a host kernel panic. The supplied panic
  identifies repeated AppleBCMWLAN DriverKit failures. Three preceding local
  driver reports on the same day contain IO80211DeadlockPolice watchdog aborts.
  This establishes a Wi-Fi driver failure, not its initiating cause or a proven
  causal link to Lumi or to the observed packet gaps. No OS/network permissions
  or interface settings were changed. Raw reports remain private.
- Live acceptance is not complete. Do not present the built fix as hardware
  verified or promote it to production based on unit tests alone.

## Targeted hardware follow-up after permission recovery

Dev-35 was installed and started after the owner authorized continuation.
CHRM and both tracks resolved, with Player 2 retaining CHRM via Player 1/LINK.
The post-reboot production engine/gateway were stopped before running Dev.
No OS network settings or permissions were changed by the test operator.

On the owner's real CDJ loop, desktop Arm/Start was exercised at zero offset.
Across approximately 157 seconds after Start, sixteen successful AutoLoop
dispatches covered BD Start, BD Chorus, the short buildup sequence and loop
re-entry. Grouping by epoch/deck/load/revision/phrase found zero duplicate
logical sends, including phrases 12 and 13 that failed in Dev-34. Those two
phrases each sent once in each of the two recorded passes. New-epoch re-entry
was not suppressed. No dispatch failures or dropped diagnostic records were
observed. Worker deadline lateness peaked at 5.533 ms; that is NOT a physical
beat-alignment measurement.

SoundSwitch visibly displayed the selected RGB bank and running BD Chorus;
Lumi remained in Start with both prepared tracks. No additional AppleBCMWLAN
crash report appeared during the bounded test. There were still occasional
stale Player status observations, so this validates the targeted duplicate-cue
repair, not overall Wi-Fi stability, physical lighting phase, a cold CDJ start,
or an extended soak. Private evidence is in `build/dev35-hardware/01..04.json`.
