# `0.4.0-dev-39` Pro DJ Link AutoLoop stability

## User-visible result

- A planned SoundSwitch AutoLoop is delegated to Lumi's realtime MIDI lane up
  to four bars before its phrase boundary. A short Pro DJ Link or UI stall near
  the boundary therefore cannot make an already prepared cue seconds late.
- Connected Live waveforms never jump backwards because an ordinary deck poll
  arrived late or out of order. Explicit seeks, Hot Cues, loads and Master
  handoffs remain immediate through their transport revision.
- Orange Live notices name Pro DJ Link, Light Output or Ableton Link and explain
  what is recovering instead of showing a generic provider warning.
- Every Dev build owns an exact matching engine and helper set. Old build
  records are replaced gracefully and child Pro DJ Link/Ableton Link processes
  are closed before the engine exits.

## Root causes

The dedicated CoreMIDI lane itself met its latency budget, but direct Pro DJ
Link only submitted work during approximately the final beat before a phrase.
If that beat was absent, the later phrase observation became the scheduling
authority and the output could be about two seconds late. The lane was fast;
its input deadline arrived too late.

Separately, SwiftUI configured AppKit sizing from `onAppear`. Installed builds
could execute that before the root `NSHostingView` existed, retaining automatic
min/ideal/max measurement and a 100–150% CPU layout loop. Delayed transport
polls could also replace the visual clock after 250 ms drift and visibly rewind
the timeline. A second invalidation source assigned the same empty local
waveform dictionary on every 4 Hz connected-deck poll. Because it was
`@Published`, that equal assignment still forced the complete Live hierarchy
through layout.

## Corrections

1. exact Pro DJ Link beats schedule the next cue within a bounded sixteen-beat
   horizon on the existing generation-safe realtime lane;
2. Bank selection is due 70 ms before the AutoLoop for the current 50 ms settle
   plus 20 ms pump budget; the user's signed offset remains part of the exact
   AutoLoop deadline;
3. transport, track-load, plan and Master changes cancel stale generations;
4. ordinary same-revision deck polls preserve one monotonic display clock;
5. AppKit disables automatic hosting-size measurements on both the real root
   hosting controller and hosting view after the window hierarchy exists;
6. service records bind to version, build, resolved engine path and executable
   SHA-256, and SIGTERM performs an orderly Rust/helper shutdown;
7. connected-deck polling only clears local waveform state when it actually
   contains data, eliminating an otherwise redundant 4 Hz SwiftUI publication.

## Automated evidence

- `lumi-engine`: predictive horizon/offset, generation, operation and canonical
  output regressions;
- `lumi-midi-output`: deadline, cancellation, capacity and latency tests;
- `lumi-prolink-input`: exact-beat ordering, bounded ingress and 50,000-update
  burst tests;
- `LumiLiveWorkspace`: 52 presentation/decoder tests, including delayed
  same-revision polls and explicit discontinuities;
- `LumiEngineClient`: real authenticated Swift-to-Rust process integration and
  fail-closed standalone Pro DJ Link behavior;
- macOS bundle build with Swift warnings treated as errors.

On the physical two-player Live screen, the equal-publication correction
reduced the paused baseline from approximately 74% to 3% UI CPU. The Rust
engine remained around 1% and the realtime output lane stayed independent.
A subsequent six-sample physical Live measurement while Player 1 was playing
measured 12.4–18.8% after warm-up; profiling no longer showed the previous
continuous root-window sizing loop as the dominant path.
A 60-second optimized lane soak emitted all 2,134 expected actions, cancelled
all 118 deliberately invalidated actions, reported zero saturation, a queue
high-water mark of 6 and 5.028 ms p95 dispatch latency.

The physical CDJ-1500X loop check stayed Ready while Pro DJ Link advanced from
961 to 1,459 observed frames. Entering Start emitted the current planned
AutoLoop immediately; Pause followed by Start advanced the pulse counter from
3 to 4 without waiting for the next phrase boundary.

After restarting a separately hung SoundSwitch process, SoundSwitch reported
one Link peer at 155 BPM and Control One connected. Lumi then completed a
controlled Arm → Start → Pause → Start → Off cycle and was left Off. This
confirms recovery of the current chain, but does not attribute the earlier
SoundSwitch application hang to Lumi without matching diagnostic evidence.

The retained 60-second lane soak and physical loop run are necessary but not
sufficient. SoundSwitch/Control One/DMX lamp response remains the final
end-to-end release evidence rather than being inferred from CoreMIDI latency
alone.
