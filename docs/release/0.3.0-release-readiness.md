# 0.3.0 – installable release readiness

Status: **Preparation required**
Datum: **2026-08-08**

## Release decision

The current product scope matches the planned `0.3.0 – SoundSwitch Live MVP`:
the real Rekordbox-backed library, Local Playback, phrase and AutoLoop planning,
automatic SoundSwitch MIDI execution and an initial physical DMX run exist.

The repository still reports `0.1.0-dev`. This is the technically current
version, but no longer an accurate next-release label. The recommended version
path is:

```text
current feature branch: 0.1.0-dev (stale canonical value)
after integration into dev: 0.3.0-dev
first installable acceptance build: 0.3.0-rc.1
accepted production commit on main: 0.3.0
next dev cycle: 0.3.1-dev or the explicitly selected next minor
```

Changing the canonical version remains an explicit product decision under
ADR-0009; it is not performed as part of this documentation update.

## Current branch and release state

Observed on 2026-08-08:

- `main` is still the initial architecture/release baseline and has no product
  tag;
- `dev` contains the previously integrated development work but not the latest
  29 commits on the active feature branch;
- the active feature branch contains all current accepted work and is 104
  commits ahead of `main`;
- no signed/notarized packaging workflow exists yet;
- the macOS target is Apple Silicon-only and embeds `lumi-engine`, but its base
  configuration explicitly disables signing;
- the existing Release app is only ad-hoc/linker signed and is not a
  distributable production artefact.

`main` must therefore not be fast-forwarded directly to the current feature
branch. The existing branch policy remains: feature PR to `dev`, release
preparation, then a deliberate `dev` to `main` release PR.

## Two distinct installable artefacts

1. **Local acceptance DMG** – useful for testing installation on the development
   Mac. It can be built without Apple distribution credentials, but Gatekeeper
   trust and clean-Mac distribution are not proven.
2. **Release DMG** – the real release candidate. The app and embedded engine are
   signed with Developer ID Application, Hardened Runtime is enabled, the DMG is
   notarized and stapled, and Gatekeeper accepts it on a clean Apple Silicon Mac.

Only the second artefact may be attached to a production GitHub Release.

## Required implementation slices

### R1 – Release configuration and version consistency

- introduce a signing-capable Release configuration without weakening the
  unsigned local verification path;
- set `VERSION`, Cargo and Apple product version to `0.3.0-dev`, then numerical
  Apple marketing version `0.3.0`;
- use a monotone `CFBundleVersion`;
- add release notes and known limitations for the RC;
- keep macOS 15 and `arm64` as the declared first-release platform.

### R2 – Deterministic app and DMG packaging

- build the Rust engine in release mode and embed it in `Contents/Helpers`;
- sign nested executables before signing the containing app;
- archive/export `Lumi.app` from a clean Release build;
- create `Lumi-0.3.0-rc.1-arm64.dmg` with an Applications shortcut;
- generate a SHA-256 checksum and a bounded SBOM;
- verify bundle identity, version, helper presence and launch before upload.

### R3 – Developer ID signing and notarization

- provision an Apple Developer Program team and Developer ID Application
  certificate;
- store the certificate and notarization credentials outside the repository;
- submit with `xcrun notarytool`, wait for acceptance and staple the ticket;
- verify the app and DMG with `codesign`, `spctl` and `stapler validate`;
- install and launch the stapled DMG on a clean Apple Silicon test account or
  second Mac.

### R4 – Product acceptance gates

- repeat the full-song SoundSwitch/DMX run after timing/lifecycle hardening;
- prove Live → Library → Live output continuity;
- complete the 100-trigger and endpoint reconnect transcript;
- record known limitations: no autonomous SMAppService yet, no production Pro
  DJ Link hardware evidence and no iPhone companion release;
- run the complete local verification gate from the exact RC commit.

### R5 – Controlled promotion to `main`

1. Squash/merge the active feature branch to `dev`.
2. Create `release/v0.3.0` from the updated `dev`.
3. Prepare `0.3.0-rc.1`, changelog, release notes and artefacts.
4. Perform installation and physical acceptance against that exact commit.
5. Set the final canonical version to `0.3.0`.
6. Merge `dev` to `main` using a normal release merge commit.
7. Create immutable tag `v0.3.0` on that `main` commit.
8. Build/sign/notarize again from the tag and publish the GitHub Release.
9. Merge `main` back to `dev` and set the next `-dev` version.

## Go/no-go

The code is ready to start R1/R2 and produce a local installable acceptance
DMG. It is not yet ready to claim production release status on `main`: signing,
notarization and the physical hardening rerun are explicit open gates.
