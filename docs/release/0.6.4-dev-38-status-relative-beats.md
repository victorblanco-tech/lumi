# Dev-38 — prevent stale bar beats from manufacturing a lead

## Scope

This addresses a reproduced provider bug, not the still-open upstream receive
latency. No waveform, MIDI mappings, output offset, Link phase, or automatic
SoundSwitch correction is changed.

The previous beat-to-position calculation chose a bar around the maximum of
the latest absolute status and our own previous position plus one. A late bar
beat could consequently be assigned to the following bar. Subsequent events
could preserve or accumulate this false lead. In the saved real session,
canonical position was 8–11 beats ahead of the latest received status; status
itself can also be late, so that difference is not a physical audio measurement.

## Change and regression

When absolute status is less than one beat old in the bridge clock, use its
nearest bar boundary instead of promoting the reference from our own position.
Older boundaries and already-accepted duplicate boundaries do not refresh the
timeline anchor. Confirmed seeks keep their explicit separate path. Sparse
status still falls back to exact-beat progression after the one-beat window.

A deterministic reordered-bar regression failed on the original code at
800 ms: position 104 instead of at most 102. It passes after the change, as do
the other 21 provider integration tests. Two pre-existing fixtures were made
temporally meaningful: the sparse-status test now emits beats at 155 BPM rather
than 100 Hz, and freshness recovery uses a new beat and receive timestamp,
not an exact replay of the old packet. No assertion was removed.

## Receive-path isolation

Bounded diagnostic probes run without the engine, MIDI, USB reads, or player
controls. They use normal discovery/session announcements and release sockets
before another receiver starts. The initial 45-second raw receiver recorded
1,500 monotone Player 1 positions; a 45-second Beat Link-only receiver recorded
1,501. These short observations do not exonerate either layer.

The complete bridge run independently with the packaged JVM recorded 1,616
positions with the expected loop wrap and two smaller backwards steps. An
IPv4-only comparison also reproduced backwards steps; that JVM option is NOT
included in the product. A longer raw comparison and desktop acceptance are
pending. Do not describe this build as a complete timing fix or show-ready.

The subsequent 150-second raw Java run recorded 4,976 Player 1 positions with
50 backwards transitions (including physical loop wraps). This reproduces
the ordering issue without Beat Link decoding, the Lumi engine, or MIDI. The
earlier short clean runs were not sufficient evidence to isolate the cause.
A Python/native-socket comparison was stopped because the macOS firewall log
reported a pending permission decision for that separate receiver. No permission
was granted or bypassed. Firewall flow evaluation is a lead, not proof of cause.

After the user confirmed the ordinary Python permission, the firewall log
recognized the receiver as allowed. A bounded Python UDP receive run, with
Java used only for normal discovery/session announcements, captured 4,970
Player 1 precise positions over 152.63 seconds. It contained one physical loop
wrap and 26 other backwards transitions, the largest 2,669 ms. Thus the problem
also reproduces outside Java's packet-receive path, Beat Link decoding, Lumi's
engine and MIDI output. This is not yet a localization to the hardware, network,
kernel or firewall. No security or network settings were changed.

A second native run enabled macOS `SO_TIMESTAMP` and read the accompanying
`SCM_TIMESTAMP` timeval with each datagram (`recvmsg`). Values/layout were
checked against the installed macOS SDK. All 5,016 Player 1 packets carried a
timestamp. Receive-call order contained 15 non-loop backwards transitions
(largest 628 ms); ordering those same packets by their kernel timestamp had
zero backwards transitions apart from the physical loop wrap. Time from that
kernel timestamp to the immediate userspace receive timestamp was median
7.937 ms, p95 155.123 ms, maximum 596.965 ms. These wall-clock differences are
local to one machine, not a calibrated CDJ-to-light measurement.

This directly localizes at least this observed reordering between the kernel
timestamp point and userspace delivery, independently of Lumi/Java decoding.
It does not identify the responsible macOS component, and is not evidence
to disable a firewall or change system policy automatically. Raw diagnostic
files remain ignored/private under `build/receive-isolation/`. Both temporary
receivers exited and released their ports; Dev-38 was reopened afterward.

## User-controlled firewall comparison

The user temporarily disabled the macOS application firewall for the requested
bounded comparison. Read-only inspection confirmed disabled state. Lumi was
closed normally and the identical native timestamp probe ran again on Ethernet,
with no build or heavy test workload. The 5,076 Player 1 samples contained two
expected loop wraps and **zero** other backwards transitions in either kernel
timestamp or userspace delivery order.

| Kernel timestamp → userspace receive | Firewall on | Firewall off |
| --- | ---: | ---: |
| Median | 7.937 ms | 0.169 ms |
| p95 | 155.123 ms | 0.275 ms |
| Maximum | 596.965 ms | 1.842 ms |
| Non-loop backwards transitions | 15 | 0 |

This strongly implicates the firewall-enabled delivery path, but the runs are
sequential observations, not proof of the exact internal mechanism. A return
to firewall-on is requested for confirmation. The user was asked to restore
the firewall immediately after this bounded run. Disabling security is **not**
a product fix or recommended operating configuration. No automatic firewall
changes, permissions changes, receive bypass, or product networking changes
were made. This comparison does not measure SoundSwitch/light beat alignment.

## Real-player desktop check

Dev-38 was opened through the desktop UI, automatically identified CHRM and
loaded both plans. Arm/Start was exercised with Player 1 running its physical
loop. Seven saved samples span 220.55 seconds and include two loop returns and
BD Start/BD Chorus transitions. All 17 recorded AutoLoop provider calls
succeeded, 0.011–5.030 ms after their scheduled deadlines, at zero output offset.
These are internal scheduling measurements, not physical beat-phase acceptance.

The previous accumulating 8–11 beat lead was not reproduced. Canonical position
relative to the latest received absolute status ranged from -1 to +2 beats,
usually 0 or +1. This comparison cannot establish audio alignment because the
status stream itself sometimes arrives late. In the final sample some triggers
preceded the reduced phrase observation by 0.64–1.21 seconds while received
status was stale. The receive-path problem therefore remains material.

Off and Quit were exercised through the UI before the independent comparison;
the engine/bridge exited and released both receive ports. No full live-output
or physical beat-phase acceptance is claimed, and this is not a main release.
