# Lumi 0.6.4-dev-33 — hardware timing investigation

This is a diagnostic development candidate, **not a claimed repair of the
late hardware starts observed with Dev-32**.

- A private, bounded `timing-diagnostics.json` flight recorder in the channel's
  data directory can be read while the Mac UI remains connected. No extra
  control connection, network listener or permission is introduced.
- Disk writes and JSON serialization run off the live engine thread. A bounded
  non-blocking queue drops diagnostics under pressure, with a cumulative loss
  count, rather than blocking output. Atomic replacement prevents torn reads.
  The file retains at most 8,192 records and is refreshed about once a second.
- Events correlate raw bridge status/beat/precise-position data and bridge/local
  queue residence with reduced position, plan preparation/edit, Arm/Start,
  scheduling generation and actual MIDI provider dispatch. Separate clock
  domains are labelled; this is not SoundSwitch or physical-light feedback.
- Changing a future Theme restores known semantic phrases that had a missing
  output mapping, then validates/materializes the newly selected Theme normally.
  Missing phrase analysis is not invented and earlier phrases are preserved.

Owner reports repeated starts improving after waiting longer. Explicitly test
immediate versus warmed Arm/Start and whether plan preparation or input age
explains the delay; do not hide variable delay with an offset.

Acceptance in progress. Do not release to main based on unit tests alone.
