# Lumi 0.4.0-dev-43 — Stable MIDI service lifecycle

## Outcome

Dev-43 separates Lumi's window lifetime from the channel engine without
allowing unattended show output. Closing or crashing the UI moves the engine
to Off and leaves Ableton Link, while `Lumi Virtual MIDI` and `Lumi Clock`
remain stable for SoundSwitch. Reopening Lumi reattaches to the same engine.

## Root causes closed

1. Carabiner shutdown and child waits could block longer than the macOS
   supervisor budget. SIGKILL of the engine could then orphan the Link helper.
2. Library revision gating left Overview and Diagnostics showing old runtime
   integration counters.
3. Removing/recreating Lumi's virtual CoreMIDI endpoints for every UI session
   could trigger SoundSwitch 2.10.3's Control One/JLC1 device-reset path.
   A five-second sample captured its main thread waiting in
   `JLC1Storage::~JLC1Storage -> std::thread::join` while the LED worker waited
   on the related recursive lock.

## Implementation

- Carabiner publish, stop, worker shutdown and child termination use bounded
  deadlines with exact-child forced cleanup.
- Lightweight snapshots refresh MIDI, Link and deck-input diagnostics without
  rebuilding or replacing Library/editor state.
- The channel engine accepts sequential authenticated UI sessions and retains
  CoreMIDI ownership across disconnects.
- Every authenticated disconnect applies Off, disables Link and reconciles
  local clock before accepting another client.
- Cleanup errors remain diagnostic and cannot terminate the engine as a
  secondary effect after the output gate is closed.
- Dev/RC/Prod service records remain database- and build-specific.
